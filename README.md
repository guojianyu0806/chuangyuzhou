## 4. 当前产品路线与验证场景

当前界面标识为「宇宙 · 传智杯独立副本」，正式参赛名称待确定。用户已确认的产品定位是：一个由用户定义、由模块构建、由AI协助搭建和持续管理的个人工作台平台。原自用工作台是可选的完整组合与示例，不预设所有用户都需要课程、六级或记账。模块库提供材料，模板提供起点，操作约束提供规则，搭建台与AI伙伴提供指引；用户可以手动搭建，也可描述自己的场景后审核AI方案。

DEV-004阶段的实现边界是已注册模块的显隐、名称、顺序，以及原有空间、卡片和业务操作。AI新增`workbenchSettings`与`workbenchModule`行动，结合已有`space`、`canvasSettings`和`canvasCard`行动参与搭建；应用前沿用真实对象查询、方案校验和确认机制。宠物式“小宇”承担入口和操作引导，该阶段未实现养成系统、自动执行、外部软件控制或新功能代码生成。DEV-009根据新授权增加`customBlock`行动，可创建配置型方块与受控小程序代码，更新代码时默认保留本方块数据，仍由用户手动运行。原宇宙已有能力和比赛新增能力分别披露，不将保留旧功能包装成本轮新增。

建议首轮场景围绕一个真实目标完成搭建与使用，例如为参赛准备选择资料、待办和日历，创建一个赛事空间，再记录要求与截止日期。先验证空白起步、模板应用、模块恢复、改名和排序等手动流程，再由用户配置本比赛专用Key并确定试测额度，用同类目标检查AI理解、提议、确认、执行和修正过程。具体任务应由真实需求与现有接口确定；不假定完整宇宙采用创宇宙的五模块或共享集合协议。

### 初始创宇宙方案（保留历史参考，不作为当前缩减范围）

此前工作名为「创宇宙」，当时建议的一句话定位为：

> 创宇宙是一款面向个人事务管理的自然语言可搭建工作台。用户可以组合模块和数据视图，核对AI提出的修改方案后执行，并查看和撤销变化。

保留通用搭建能力。会议与部门活动管理作为首个重点验证及演示场景，不把整个平台改成只能处理会议的固定工具。它接近赛道推荐的低代码与智能工具构建方向，也体现个人效能价值；这是本项目的适配判断，不是官方对作品的分类或认可。

### 初始路线为何选择普通上班族模板

app/ 中保留的模板包含月度工作、会议、部门活动和生活安排。选择会议与部门活动这条主线，能直接使用已有模块，减少新增样板页面，同时让评委看到输入、处理和实际结果。模板里20条事务与6份资料是明确标记的虚构样例，不能当真实使用案例。

初步目标用户：需要自己跟进会议任务和部门活动的人。任务里记录同事或负责人姓名，不代表系统已具有多人登录、团队权限或实时协作能力。

待通过用户验证的需求假设：事项散落在文字记录中；手动搬运日期和负责人容易遗漏；同一事项在不同视图重复维护；用户希望AI能实际更新工作台，同时能检查和纠正修改。

如后续更容易接触校园项目负责人，可复用同一套机制换成校园项目场景。选择依据是实际需求与验证便利，不额外平行建设多套行业功能。

### 初始创宇宙路线的任务草案

1. 用户选模板或空白创建空间，自行组合文本、列表、看板、日历、资料模块。
2. 粘贴一份明确标记的模拟会议记录，或经授权的脱敏文字材料。
3. 让AI提出任务及字段修改方案，显示目标、负责人、日期和对应原文。
4. 对缺少日期、负责人不清或存在冲突的内容，显示待确认信息；澄清期间不自动执行写入。
5. 用户核对并确认，列表、看板、日历读取同一批已保存记录。
6. 用户提出临时变化，例如延期、换负责人或修改某条任务；能明确理解这次改动影响哪些对象。
7. 展示确认后的回执；按实际依赖和版本情况撤销，冲突时解释原因。

这些步骤属于app/的历史拟验收主线，DEV-001已完成离线连续修订验证，但未完成真实模型验证。它们不会自动成为yuzhou/本轮验收范围，也不据此删除完整宇宙中的任何业务。

### Git日志是必需材料，按真实迭代及时提交

官方赛道“代码仓库与演进记录”明确要求完整、细粒度的Git历史，禁止一次性提交全部功能，每次提交应对应核心AI对话或功能模块落地。只交最终源码压缩包或一份手写开发总结，不能替代仓库历史。[规则来源](https://www.boxuegu.com/matchTrack/detail/?id=10039)

本项目采用以下节奏；这是执行约定，不是官方指定的提交数量：

| 真实阶段 | 什么时候提交 | 应说明什么 |
| --- | --- | --- |
| 需求与设计 | 一项明确需求或方案形成后 | 场景、目标、限制、选型依据；计划不得写成实现 |
| 功能实现 | 一个可检查的功能阶段完成后 | 实际新增行为、影响范围、检查结果 |
| 问题修复 | 复现原因明确且针对性修复后 | 触发条件、原因、修改和复验；保留有代表性的真实失败 |
| 独立重构 | 一项职责或结构调整完成后 | 调整原因、行为是否变化及验证依据 |
| 验证与材料 | 有实际新结果或相应文档更新后 | 检查对象、结果、限制、对应源码版本 |

同一迭代的代码、针对性验证和必要说明可一起提交，不要求人为拆成多个commit。完成阶段后及时留存，再推进下一独立任务；禁止最后才集中补提交，也禁止凑次数、空提交、伪造历史或重排时间来营造不存在的过程。

建议提交格式：

```text
fix(planner): 保留未确认方案的后续修订上下文

目的：说明实际复现的问题和影响。
改动：概括本次真正完成的变化。
验证：列明执行结果；未验证或失败须明示。
关联：DEV-001（原始开发对话与专业化需求说明的索引）。
```

以上只是格式示例，不是已经发生的修复或提交。标题不用直接照抄用户口语，也不能只写“更新”“完成”“优化”。消息中不包含密钥或私人原文。

每条核心迭代记录建议包含：记录编号、实际日期、专业化需求、原始对话定位、AI方案及修改、人类决策或反馈、关联文件、验证结果和限制。Git提交引用稳定记录编号；提交完成后，证据索引再从真实历史关联commit hash，不反复修改同一提交只为回填自身hash。

后续实施前检查仓库状态及已有历史；新建仓库须从真实基线开始。旧代码首次导入注明来源和实际时间，不将基线导入声称为完整从零开发史。不要在交付前把关键演进压缩为一个commit。本文规定本地留存方式，不授权远端创建、公开或推送；最终按赛事要求提供可访问仓库和必要的日志导出。

### 用户提示词专业化整理与原始证据分开

用户日常表达可以是口语。正式需求说明、技术方案、开发总结、Git说明和视频解说采用忠实的专业化转述，不直接把聊天逐句搬进去；优化语言不改变原意，不补造技术细节或已完成结果。

| 材料层 | 写法 | 真实性边界 |
| --- | --- | --- |
| 原始开发证据 | 保留实际输入、AI回复、追问和修复的顺序，附真实时间或对话定位 | 不润色替换；可生成标注脱敏的提交副本，保留本地原件 |
| 需求与过程整理稿 | 按场景、问题、目标、约束、验收条件转述，提炼设计决策与迭代结果 | 注明“根据原始对话整理”，与原始证据编号对应，不声称为原始Prompt |
| 正式参赛说明 | 用连贯专业文字解释问题、方案、实现和验证，只陈述有依据的贡献与结果 | 官方要求的原始Prompt快照另行对应提供，不能由润色稿取代 |

专业化示例（仅说明整理方法，非已有原始聊天引文）：

> 口语示例：AI先告诉我准备改哪里，我点了以后再改，改错了还能退回去。
>
> 需求整理：系统应在执行AI生成的修改方案前展示受影响对象及字段变化，经用户确认后保存。对已执行变更提供撤销入口；出现后续编辑或依赖冲突时，阻止覆盖并说明原因。

上例中的冲突处理细节若不是用户原话，应标明为结合已有实现提出的设计补充，不倒写为用户曾完整提出。对于信息不足的表达，记录待确认项，不靠专业措辞掩盖缺口。

后续可以先形成更明确的开发任务说明，再实际用于AI协同开发并保留对应过程。事后润色的提示词只能作为整理稿；只有确实发出并参与了开发的文本才能记为当轮真实Prompt。

### 至少三条真实核心开发链

以下三类主题适合在实际发生时整理为开发Prompt链：

1. 连续需求修订：复现“把刚才安排改到周五” → 定义方案上下文 → 与AI讨论方案 → 实际修改 → 复验。
2. 可理解的受控修改：发现字段或来源展示问题 → 明确意图和约束 → 修改交互或校验 → 验证错误路径。
3. 共享视图与可靠撤销：复现真实数据一致性或撤销问题 → 定位原因 → 引导AI修复 → 确认恢复行为。

最终选择真实发生的至少三次核心功能迭代。每条建议保存：真实需求、原始对话或录屏、采用及未采用方案的理由、相关真实提交、失败与修复、检查结果。既有能力若无需再改，使用其真实原始开发链；不能编造新的开发过程。

### 小规模用户验证

建议邀请3—5名能代表目标场景的人，完成2—3项明确任务。记录他们原本怎样做、在工作台里哪里理解困难、核对与纠错耗时。若比较手动方式与AI方式，材料和目标保持可比，计时包含阅读、等待、确认和纠错；小样本只支持具体任务结论。

### 复现验证

后续在独立干净目录或另一台可用设备，按实际交付说明验证运行时准备、首次初始化、模型配置、应用启动和核心任务。分别记录环境准备与启动/任务耗时，并说明网络、Key等前提。只有实际计时通过后才写“已满足10分钟复现”；不得把运行中的私人服务地址当完整复现方案。
