# DEV-001：未执行AI方案的连续修订

日期：2026-10-08。本文根据项目规划与实际源码核查整理，属于专业化开发记录，不是用户原始Prompt。

## 来源与目标

原始实施授权见 raw/2026-10-08-start.txt；具体功能优先级来自当前README第6、7节。原始开发会话为本Codex聊天“总结传智杯比赛基本信息”，以及本轮后端和前端子任务。后续按真实过程补充，不伪造完整导出。

用户希望工作台适合比赛，并按真实阶段提交。代理据此选择先解决连续修改缺少上下文的问题：对尚未执行的方案提出追问时，系统应理解相关前文，展示新的完整方案并继续等待确认。

## 静态问题证据

- 旧前端 ai-form 提交会先取消当前proposal，然后只发送新message。
- 旧server调用planner时没有服务端保存的前文。
- 旧planner只包含本轮输入和已保存空间；未确认预览不能作为已保存业务状态。

## 本轮采用的设计

服务端管理contextId，客户端只携带标识，不提交任意对话历史。上下文限定原工作区和基线版本，设置轮次、长度和有效期上限。真实用户历史用于证据定位，AI说明不作为用户事实来源。新的有效方案生成后才替代旧方案；失败时保留旧方案。

前端明确当前是在继续修改还是新话题。输入草稿、取消、确认、空间切换、过期和历史恢复都按同一上下文规则处理。新话题结束未执行方案，不宣称已经完成业务操作。

## 验收目标

1. 第一轮方案未执行，第二轮能改变其指定部分并产生完整替代方案。
2. 澄清后续答保留原需求，不捏造来源。
3. 修订失败时原草稿仍可查看并按规则确认；成功后旧草稿不能重复执行。
4. 跨空间、过期、版本变化、取消或确认中的请求不得误写。
5. 确认前业务状态保持不变；界面能清楚显示修改前后。
